# Supplementary reading – Authentication and Credential Management

This chapter explains how web applications verify identities, protect authenticators, and maintain authenticated sessions.

## Authentication and identity

A digital identity represents a person, service, device, or other subject within a system.
An identifier, such as a username or service name, tells the system which identity is making a claim.
Authentication checks whether the subject controls an authenticator associated with that identity.

Identity proofing connects a digital identity to a real person or organization when that connection is required.
Many applications authenticate pseudonymous users without establishing their legal identity.
Authorization uses the authenticated identity and other context to decide which actions are allowed.

Authentication involves several related elements:

- An identity represents a subject within a defined system
- An identifier names or selects that identity
- An authenticator provides evidence that the subject controls something bound to the identity
- A credential records or carries information used in an authentication process
- A session preserves the result of authentication across later requests

Both people and software need identities.
Human identities include customers, employees, administrators, and support staff.
Non-human identities include applications, services, devices, scheduled jobs, and deployment processes.
Giving each workload its own identity makes its credentials, activity, and access easier to control and investigate.

Authentication factors fall into three categories:

- Knowledge, something the subject knows, such as a password or personal identification number
- Possession, something the subject has, such as a security key, certificate, or device containing a cryptographic key
- Inherence, something the subject is, represented by a biometric characteristic

Multi-factor authentication (MFA) requires evidence from different categories.
Two passwords provide two knowledge checks and remain single-factor authentication.
Location, device reputation, and behavior are risk signals that can influence an authentication decision.
They are not additional authentication factors.

The appropriate method depends on the subject, threats, usability needs, and required assurance.
A public discussion forum and an administrative interface for financial transactions have different authentication requirements.
Every route to protected functionality needs equivalent authentication strength, including APIs, mobile clients, support tools, and recovery flows.

Established identity services and framework features reduce the amount of security-sensitive code maintained by an application team.
The application team still owns the configuration, integration, session handling, and validation performed by its application.

## Passwords and credential lifecycle

Credentials remain sensitive throughout their lifecycle.
A secure login cannot compensate for a password exposed in source code, a recovery token that never expires, or an API key that remains active after its owner leaves.

The lifecycle includes:

- Enrollment and provisioning, binding a new authenticator to the intended identity
- Issuance and delivery, transferring the credential through an appropriate protected channel
- Storage and use, preventing disclosure while the credential is at rest, in transit, and being processed
- Replacement and rotation, introducing a new credential without creating an avoidable outage or insecure fallback
- Revocation, preventing further use after compromise, loss, or removal of access
- Recovery, restoring access after the normal authenticator becomes unavailable
- Retirement, removing credentials and related access when the identity or integration is no longer needed

### Password policy

Password rules should help users choose unique passwords and use password managers.
Useful controls include:

- Allowing long passwords and passphrases
- Allowing paste and password-manager autofill
- Comparing new passwords with lists of common and breached passwords
- Preventing silent truncation
- Avoiding composition rules that predictably force uppercase letters, digits, and symbols
- Requiring a password change when compromise is known or suspected
- Avoiding routine password changes without evidence of compromise

Authentication responses should avoid revealing whether a username or email address exists when that information is sensitive.
Similar response content and timing across login and recovery paths reduce account-enumeration opportunities.

Rate limits, increasing delays, and detection controls make automated guessing more expensive.
A fixed account lockout can let an attacker deny access to a known user, so its availability consequences need consideration.
Password controls should address brute force, password spraying, and credential stuffing without creating a simple denial-of-service mechanism.

### Password storage

Applications store a verifier produced by a purpose-built password-hashing algorithm.
Password hashing is deliberately expensive so that each offline guess costs an attacker time and computing resources.

An appropriate design includes:

- A current password-hashing algorithm, such as Argon2id or another algorithm recommended by the OWASP Password Storage Cheat Sheet
- A unique random salt for each password, normally generated and managed by the password-hashing library
- A work factor selected for the application's environment and increased as hardware improves
- A migration plan for hashes whose algorithm or work factor becomes outdated

Reversible encryption and fast general-purpose hashes provide inadequate password storage.
An optional pepper adds a secret value kept separately from the password database.
Compromise of a pepper requires a planned way to reset affected passwords because existing hashes cannot be recreated without the old value.

### Recovery and authenticator changes

Attackers often target password reset and authenticator replacement because these paths can bypass the normal login method.
Recovery should provide comparable assurance to the authentication method it replaces.

A typical password-reset flow uses a random, single-use token with a short lifetime.
The application stores the token securely, limits repeated requests, returns a neutral response, and sends the token through a previously verified channel.
After a successful reset, the application notifies the user and offers to terminate other active sessions.

Changes to an email address, phone number, passkey, or MFA method affect future authentication.
These changes require recent authentication and a notification through an existing trusted channel.
Recovery codes need sufficient entropy, secure display and storage, and invalidation after use.

### Non-human credentials

Applications and services may authenticate with API keys, client secrets, service-account credentials, certificates, or platform-managed identities.
Each credential needs a named owner, defined purpose, limited lifetime, and revocation process.

Long-lived shared secrets are difficult to attribute and rotate.
Managed workload identities and short-lived credentials reduce the number of static secrets that teams must distribute and store.
Mutual Transport Layer Security (mTLS) authenticates a client and a server with certificates during the connection.
Its security depends on trusted certificate issuance, private-key protection, certificate validation, renewal, and revocation.

Credentials do not belong in source code, container images, URLs, command-line arguments, logs, or client-side application bundles.
A database connection string may contain a username and password, which makes the entire value a secret.
Applications should obtain such values from an approved configuration or secrets-management mechanism at runtime.

## Multi-factor authentication and passkeys

MFA limits the damage caused by one compromised factor.
The strength of the result depends on the selected methods and every enrollment, replacement, recovery, and fallback path.

Common methods have different properties:

- SMS codes add a possession check but remain exposed to phishing, SIM swapping, and weaknesses in the telephone network
- Time-based one-time passwords (TOTP) resist password reuse but can be captured by a real-time phishing site
- Push approval is convenient but can lead to authentication fatigue when repeated prompts encourage accidental approval
- Security keys use origin-bound public-key authentication and resist common phishing techniques
- Passkeys use FIDO2 and Web Authentication (WebAuthn) public-key credentials held by an authenticator
- Backup codes provide recovery access and therefore need protection comparable to another authenticator

A passkey stores a private key in an authenticator and registers the corresponding public key with the service.
The authenticator proves possession by signing a challenge for the service's origin.
A device PIN or biometric check may activate the authenticator locally.
The biometric data normally stays with the device instead of being sent to the web application.

Some passkeys synchronize across a user's devices, while others remain bound to one device or hardware security key.
An application should base its assurance decision on properties it can verify rather than assuming every passkey is hardware-bound.

Phishing-resistant authentication is especially valuable for administrators and access to sensitive data or operations.
Step-up authentication requests stronger or more recent evidence when the risk of an action increases.
Examples include changing authentication factors, viewing recovery codes, or approving a financial transaction.

MFA enrollment and replacement require recent authentication.
The application should notify the user when a factor is added, removed, or recovered.
A fallback that accepts a weaker factor can reduce the strength of the entire authentication design.

Email sign-in links and one-time codes are bearer credentials delivered through another channel.
They need a short lifetime, single-use enforcement, and protection from disclosure or replay.
The application binds each value to the intended account and authentication request.

## Authenticated sessions

HTTP treats each request independently.
After login, a web application usually issues a session token that links later requests to the authenticated identity.
Anyone who can present a bearer session token can normally act as that identity until the token expires or is revoked.

Sessions can use different token designs:

- A reference token is an unpredictable identifier that points to session state held by a trusted backend
- A self-contained token carries claims that a receiving service validates without retrieving all session state from the issuer

Cookies and HTTP authorization headers are ways to transport tokens.
They do not determine whether the token is reference-based or self-contained.
Reference tokens make immediate server-side invalidation straightforward.
Self-contained tokens require a revocation design when access must end before their expiration time.

### Protecting session tokens

Session identifiers need enough entropy to prevent guessing and should reveal no sensitive meaning.
The trusted application layer validates the token on every protected request.
Tokens need protection from disclosure in transport, browser storage, URLs, error messages, and logs.

For cookie-based sessions, important attributes include:

- `Secure`, which limits transmission to HTTPS connections
- `HttpOnly`, which prevents client-side scripts from reading the cookie
- `SameSite`, which controls when the browser includes the cookie in cross-site requests
- `Domain` and `Path`, which should limit the hosts and paths that receive the cookie

Cookie name prefixes let supporting browsers enforce additional restrictions.
A cookie whose name begins with `__Secure-` must be set over HTTPS and include the `Secure` attribute.
A cookie whose name begins with `__Host-` must also use `Path=/` and omit the `Domain` attribute, which prevents other hosts and narrower paths from setting a cookie with the same name.
The `__Host-` prefix is usually the stronger choice for a session cookie that only one host needs to receive.

`SameSite=Strict` provides the strongest restriction on cross-site requests.
`SameSite=Lax` permits some top-level navigations, while `SameSite=None` permits cross-site use and requires `Secure`.

`HttpOnly` reduces direct token theft through injected scripts.
An injected script can still send requests from the user's browser, so preventing cross-site scripting remains essential.
Script-accessible storage such as `localStorage` exposes bearer tokens to any script that runs in the same origin.

Browsers automatically attach matching cookies to requests.
This behavior creates cross-site request forgery (CSRF) risk for state-changing operations.
An appropriate `SameSite` setting contributes to the defense, while application-specific request-forgery controls remain necessary where cross-site requests are allowed.

### Session lifecycle

A session design defines:

- Creation after successful authentication
- Renewal after authentication, re-authentication, and privilege changes
- Idle timeout after a period without activity
- Absolute lifetime regardless of activity
- Rules for simultaneous sessions on several devices
- Re-authentication before sensitive changes or operations
- Termination during logout, account disablement, credential compromise, and expiration

The server enforces timeouts and termination.
Removing a cookie from one client leaves server-side session state active unless the server invalidates it.
Federated applications also define how local sessions relate to the identity provider's session and logout behavior.

Session fixation occurs when an application keeps a session identifier that an attacker knew before the victim authenticated.
Issuing a new identifier after authentication and privilege changes breaks that link.
Session hijacking occurs when an attacker obtains and presents a valid session token.
Transport protection, safe storage, short exposure windows, renewal, re-authentication, and termination reduce that risk.

## Federation, single sign-on, and tokens

Single sign-on (SSO) allows a user to authenticate once and access several applications.
Federation allows one security domain to rely on identity information from another domain.
Centralized authentication can improve consistency and account removal, while a compromised or misconfigured identity provider can affect every relying application.

Common federation and authorization terms include:

- An identity provider authenticates a subject and provides identity information to a relying party
- A relying party trusts the identity provider and establishes its own application session
- OAuth 2.0 provides delegated authorization to protected resources
- OpenID Connect (OIDC) adds an identity layer to OAuth 2.0 and provides an ID token for authentication
- Security Assertion Markup Language (SAML) carries signed assertions between an identity provider and a service provider
- SSO describes the user experience rather than one specific protocol

OIDC and SAML serve the same general purpose in federated authentication and SSO.
An application integration chooses one of these protocols rather than combining them in the same authentication flow.

In a SAML integration, the identity provider sends identity information to the service provider in an XML assertion.
The service provider validates the assertion's signature, issuer, audience, recipient, response binding, and validity conditions before accepting it.

Applications should use established protocol libraries and a trusted configuration for expected issuers, endpoints, algorithms, and keys.
Values found inside an untrusted token must not select a new issuer or key source without validation against that configuration.

### Redirect-based flows

An OIDC client commonly redirects the browser to an identity provider and receives an authorization response at a registered callback URI.
Several values bind the steps of that flow together:

- An exact redirect URI prevents an authorization response from being delivered to an attacker-controlled location
- `state` binds the response to the browser interaction that started the request and helps prevent request forgery
- `nonce` binds an ID token to the authentication request and helps detect replay or token injection
- Proof Key for Code Exchange (PKCE) binds an authorization code to the client instance that initiated the flow

The client validates these values before establishing its local session.
Alternative login and callback endpoints need the same controls as the primary path.

### JSON Web Tokens

A JSON Web Token (JWT) uses a compact token format.
A signed JWT contains a header, a payload of claims, and a signature or message authentication code.
The header and payload use `base64url` encoding, which makes them transportable and readable but provides no confidentiality.
Encryption is a separate operation.

Before accepting a JWT, the receiving application validates:

- Integrity with an expected signature or message authentication code
- An explicitly allowed algorithm
- Key material from a trusted source for the configured issuer
- The expected issuer and audience
- The validity period, including expiration and any not-before constraint
- The token type and intended purpose
- Flow-specific values such as an OIDC `nonce`

Signing protects integrity and authenticity without hiding the claims.
Token payloads should contain only the information required by the receiving component.
Passwords, private keys, recovery data, and unnecessary personal information do not belong in readable claims.

### Token purposes

Token types are not interchangeable.
An ID token provides authentication information to its intended OIDC client.
An access token authorizes access to a resource server.
A refresh token obtains new tokens and needs stronger storage and lifecycle controls because it may remain useful for longer.
An application session token represents the application's own authenticated session.

## Authentication failures and testing

Authentication failures often appear outside the main login form.
Registration, password reset, factor recovery, API authentication, SSO callbacks, remember-me features, and support tools all affect the authentication boundary.

Automated attacks use credentials in different ways:

- Brute force tries many candidate passwords against an account
- Password spraying tries a small set of common passwords against many accounts
- Credential stuffing reuses username and password pairs exposed by another service
- Authentication fatigue sends repeated approval requests in the hope that a user accepts one

Account enumeration helps an attacker select targets by revealing whether an identifier exists.
Differences in messages, status codes, response bodies, redirects, and timing can all provide that signal.

An authentication test plan covers the complete lifecycle:

- Successful and failed authentication for every supported method
- Missing, incorrect, expired, revoked, replayed, and malformed credentials
- Password creation, change, reset, and recovery
- MFA enrollment, use, replacement, fallback, and recovery
- Session creation, renewal, timeout, concurrent use, logout, and revocation
- Federated login with invalid signatures, issuers, audiences, redirect URIs, state, nonce, and validity periods
- Direct requests to protected endpoints without following the user interface
- Equivalent controls across web pages, APIs, mobile clients, and administrative paths
- Rate limiting and resistance to user enumeration
- Absence of passwords, tokens, and other credentials from logs and error responses

Positive tests verify that valid authentication attempts succeed and create the expected session.
Negative tests verify that the application rejects missing, invalid, expired, replayed, or tampered authentication data without disclosing sensitive information.
Including these tests in the regression suite helps detect security weaknesses introduced by changes to authentication code, configuration, or identity-provider integrations.

## Reviewing an authentication flow

Consider an invoice application that delegates employee authentication to an OIDC provider.
After federated login, the application creates its own server-side session.
A scheduled billing job authenticates separately with a managed workload identity.

The design produces specific security requirements:

- The application uses the OAuth Authorization Code flow with an exact redirect URI, `state`, `nonce`, and PKCE
- The application exchanges the authorization code at the configured token endpoint and accepts tokens only from the configured issuer
- The application validates each token's signature, algorithm, audience, purpose, validity period, and flow-specific claims
- Successful authentication replaces any pre-authentication session identifier
- The session identifier is random and travels in a cookie with `Secure`, `HttpOnly`, and an appropriate `SameSite` value
- The server enforces idle and absolute timeouts and invalidates the session during logout or account disablement
- Changes to authentication factors require recent authentication and notify the employee through an existing channel
- The billing job receives a short-lived identity from the platform instead of a password embedded in a connection string

The requirements lead to positive and negative tests:

- A valid response from the configured provider creates a new application session
- A token with a modified signature, wrong audience, wrong issuer, expired lifetime, or wrong purpose is rejected
- A callback with missing or incorrect `state` is rejected, and an ID token with an incorrect `nonce` is rejected
- An authorization code cannot be exchanged without the matching PKCE verifier
- A session identifier observed before login cannot access the authenticated session
- An expired or logged-out session cannot access an invoice
- A disabled employee cannot retain an active application session
- The billing job cannot authenticate with an expired workload credential

This example connects the identity-provider configuration, token validation, session lifecycle, non-human identity, and regression tests.
A change to any part of the flow requires a review of the related requirements and tests.
